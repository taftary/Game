# ADR-004: Save binary encoding — autosave format + atomic rotation

- **Status:** binding (2026-09-17, landed with
  `plans/v0.3.0/autosave-persistence`; proposed by navigation-engine spec
  [`cosmic-navigation-engine-v0.4.md`](../techstack/cosmic-navigation-engine-v0.4.md)
  §10)

## Context

The navigation engine needs deterministic resume across sessions.
Procedural regions are never saved (they regenerate from seeds, spec §6),
so the save payload is small and fixed-shape. The spec resolves
persistence as **binary autosave**.

## Decision

- **Persist:** ship state (active-frame ID, 6D position/velocity in that
  frame, orientation quaternion, mass, fuel, active control state);
  navigation state (select-to-focus target, active transition plan,
  time-compression mode/multiplier); metadata (format version, master
  seed, real-world + simulation timestamps, session playtime,
  data-catalog version IDs, integrity checksum).
- **Autosave triggers:** confirmed active-frame transitions, completed
  SOI handoffs, start/completion of an automated fly-to, explicit
  suspend/quit, and a user-configurable periodic interval.
- **Writes are atomic:** temporary file + rename; retain at least two
  rotating recovery snapshots.
- Procedural content stays unsaved by construction (determinism rule,
  spec §6).

## Consequences

- Migration strategy keys off the format-version field in metadata;
  readers must reject unknown versions cleanly (checksum verified first).
- [`../techstack/persistence.md`](../techstack/persistence.md) gains the
  concrete field layout when `plans/v0.3.0/autosave-persistence` is planned.
